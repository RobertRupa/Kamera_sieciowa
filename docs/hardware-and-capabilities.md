# Hardware Manifest + Capability Registry

## Purpose: avoid hardware guesses and duplicated feature flags

**Hardware Manifest** is the versioned single source of truth for a specific **PCB revision**. It records the primary ESP-IDF target, Flash/PSRAM, Wi-Fi companion/transport, LCD/touch, GPIO/buses, security key-storage prerequisites, firmware policy and evidence for each verified fact. An unknown GPIO is explicitly `null`, never silently assigned.

**Capability Registry** is a small pure C++ component. It computes a read-only snapshot from three independent inputs:

```text
  Verified Hardware Manifest     Build-time feature selection     Runtime service status
           |                                |                               |
  BoardProfile (board support)          BuildFeatures                    RuntimeState
           |                                |                               |
           +--------------------------------+-------------------------------+
                                            |
                                 CapabilityRegistry::snapshot()
                                            |
                        +-------------------+------------------+
                        |                                      |
                   WebGUI /api/v1                       LVGL Presenter
                (typed read-only DTO)                 (no direct driver queries)
```

This is not a “service locator” or mutable global flag bank. The registry performs **no ESP-IDF I/O, NVS writes, heap allocation or hardware probing**. An application service assembles a coherent `RuntimeState` from actual initialized drivers. BSP/board-support modules alone are responsible for compiling the **verified** static profile. The UI is a consumer; it cannot independently declare support for a feature.

The sample manifest describes a **possible ESP32-P4 + ESP32-C6 topology**, not a pin-compatible or production-ready JC4880 board description. ESP32-P4 has no on-chip Wi-Fi; host connectivity requires verified companion bus, firmware and driver. ESP-IDF supports approaches including `esp_wifi_remote` and `esp-extconn` for supported setups. Never infer actual link pins from another board.

## Capability status contract

| State | Static hardware | Compiled component | Runtime | Frontend behavior |
| --- | --- | --- | --- | --- |
| `unsupported` | absent | irrelevant | irrelevant | hide feature |
| `unverified` | unknown pinout/key scheme | any | any | block, show diagnostic |
| `disabled` | verified | not built | irrelevant | show disabled/omit |
| `not_ready` | verified | built | waiting/not initialized | status with retry if appropriate |
| `ready` | verified | built | prerequisite check passed | allow UI action subject to authentication |

**Supported** and **ready** are not interchangeable. When Wi-Fi link becomes ready, the wizard is still unavailable until *real* encrypted NVS is initialized. mDNS requires the relevant network interface to have an IP, not merely a compiled mDNS component. LVGL requires an initialized verified display and a running GUI task; touch is independent, because LVGL can work without a touch panel.

The five statuses are snapshots, **not** permission grants, locks or proof of encryption. Individual operations must still validate authorization, the current connection state and their own failure paths. Snapshot expiry is implicit: recompute at request/update time.

## Component contract

`BoardProfile.hpp` holds `BoardProfile`, `WifiTopology` and `Verification`. The example `makeIllustrativeP4C6Profile()` returns `Unverified` for radio link, display, touch and NVS key scheme. There is no autogenerated claim that these peripherals work.

`CapabilityRegistry.hpp` defines `Feature`, `BuildFeatures` and `RuntimeState`, with const methods:

```cpp
CapabilityRegistry(BoardProfile board, BuildFeatures built) noexcept;
CapabilityState get(Feature feature, const RuntimeState& live) const noexcept;
CapabilitySnapshot snapshot(const RuntimeState& live) const noexcept;
static const char* featureKey(Feature feature) noexcept;
static const char* stateKey(CapabilityState state) noexcept;
```

To integrate in an application, set `main/CMakeLists.txt` to depend on `board_capabilities`; build `BoardProfile` from the verified manifest, derive `BuildFeatures` from Kconfig/compiled modules and collect `RuntimeState` from injected real service ports (network, NVS, HTTP, LVGL). A C++17-safe example:

```cpp
using namespace board_capabilities;
const BoardProfile board = /* compiled verified BSP profile */;
BuildFeatures built{};
built.wifiAdapter = true;         // from Kconfig / linked module state
built.webgui = true;
built.encryptedNvs = true;
CapabilityRegistry registry(board, built);

// Populate from actual service snapshots, not guessed values.
RuntimeState live = /* coherent snapshot from services */;
const auto capabilities = registry.snapshot(live);
const auto web = registry.get(Feature::WebGui, live);
```

`BuildFeatures` flags and service snapshots above are **illustrative**, not proof that WebGUI or encrypted NVS exists. Production components must derive them correctly and test them on the board. Verify at boot that the actual `IDF_TARGET` agrees with the hardware profile. The `BoardProfile` string pointers should refer to static literals with lifetime longer than the registry.

## REST output example (hypothetical running board)

Suggested authenticated `GET /api/v1/device/capabilities`:

```json
{
  "data": {
    "schema_version": 1,
    "board_id": "example-esp32p4-c6-display",
    "target": "esp32p4",
    "wifi_transport": "companion",
    "capabilities": {
      "wifi": "ready",
      "wifi_wizard": "unverified",
      "captive_portal": "unverified",
      "mdns": "not_ready",
      "webgui": "ready",
      "display": "unverified",
      "touch": "unverified",
      "lvgl": "unverified",
      "encrypted_nvs": "unverified"
    }
  }
}
```

Here we **hypothetically** verified Wi-Fi companion transport and started an IP/HTTP server, but NVS protection and LCD/touch remain unverified. This JSON is **not** produced by the shipped unverified `BoardProfile` without adapting its hardware fields. Serialize with `featureKey`/`stateKey`; never expose raw driver objects or secrets. A captive provisioning UI gets only its minimal public allowlisted capabilities; protect richer device profile endpoints behind authentication.

## Agent responsibilities
- **BSP/Hardware agent**: owns `docs/hardware/board.json`, schematic citations and verified `BoardProfile`; never invents pin or Flash sizes.
- **Security/Connectivity agents**: own live transport, IP, NVS encryption verified-state probes and their service contracts. Mark `ready` only after initialization and actual checks, not build flags.
- **Architecture/Application agent**: owns registry rules/contracts and host tests; keeps component free of ESP-IDF coupling.
- **Frontend and LVGL agents**: consume the same snapshot; hide/disable actions by state rather than duplicating driver detection.
- **QA agent**: validates manifest structure/evidence, exercises startup/failure transitions, confirms real target build, reviews whether ready was spuriously inferred.

Treat absence of a feature as an explicit capability, not a crash. Registry use should not spawn per-feature tasks, introduce a huge factory hierarchy or reimplement ESP-IDF services.
